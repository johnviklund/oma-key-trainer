# Omarchy Keybindings Trainer — PRD

**Date:** 2026-09-13
**Status:** Draft — requirements only, not yet planned or implemented

## Summary

An Omarchy plugin, opened from the existing top-right menu like other
built-in entries, that helps users learn Omarchy's Hyprland keybindings. v1
shows a static reference list of the ~10 most useful bindings. v2 turns it
into a background-tracked drill: each binding's real usage counts up, and
reaching 10 uses marks it complete, moves it to the bottom of the list, and
pulls the next not-yet-learned binding from a larger curated pool into the
top slot.

## Problem Frame

Omarchy's keybindings cover most day-to-day window management, but there's
no way for a user to discover or reinforce the ones that matter most short
of reading documentation or trial and error. New keybindings are easy to
forget after a first read; nothing in the desktop today rewards actually
using them until they're second nature.

## Requirements

**v1 — Static list**

- R1. The plugin adds one entry to Omarchy's existing top-right menu,
  matching the visual and interaction style of other built-in menu entries
  (open/close behavior, box styling).
- R2. Opening the entry shows a box listing a curated set of the ~10 most
  useful Omarchy/Hyprland keybindings, each row showing the key combination
  and a short description of the action it performs.
- R3. v1 is view-only — no counters, tracking, or interactivity beyond
  opening and closing the box.

**v2 — Usage tracking and rotation**

- R4. Each visible row displays a usage counter to the right of the
  keybinding, starting at 0.
- R5. The plugin counts each keybinding's usage continuously in the
  background — for every keybinding in the pool, whether currently visible,
  already completed, or waiting in the rotation — regardless of whether the
  box is open. Counting does not stop once a keybinding passes its
  10-use completion threshold.
- R6. Usage counting covers only Omarchy/Hyprland system-level keybindings
  (window management, workspaces, app launching, screenshots, etc.).
  Application-specific shortcuts are not tracked.
- R7. Usage is matched to the underlying action a keybinding triggers, not
  to the literal key combination. A user's personal rebinding of a key does
  not break counting for that action, though the row still displays the
  plugin's default key text. (Governs display accuracy caveat — see Key
  Decisions.)
- R8. When a keybinding's counter reaches 10, it is marked complete, moved
  to the bottom of the visible list, and the next not-yet-learned keybinding
  from the curated pool is inserted at the top.
- R9. The curated pool that supplies both the initial ~10 and later
  rotations is larger than the visible list and ordered by the plugin author
  in a fixed sequence. New entries are pulled in that order, never randomly.
- R10. There is no way to manually mark a keybinding complete or skip it —
  completion results only from real recorded usage.
- R11. Once every keybinding in the curated pool has been completed, the
  plugin shows an all-learned/fully-complete state instead of pulling in
  further rotations.
- R12. Progress (per-keybinding counts, completion state, current rotation
  position) persists across reboots and logins.

## Key Decisions

- **Tracking is scoped to Hyprland/Omarchy system-level keybindings only.**
  App-specific shortcuts have no shared, generically observable event
  source, so tracking them system-wide isn't feasible without per-app
  integration. (session-settled: user-approved — chosen over including
  in-app shortcuts: infeasible to observe generically without per-app
  work.) Governs R6.
- **The keybinding pool is a curated static list shipped with the plugin,
  not parsed from the user's live Hyprland config.** Simpler to build and
  maintain, at the cost of the displayed shortcut potentially not matching
  a binding the user has personally rebound. (session-settled: user-approved
  — chosen over live-parsing the user's config: avoids config-parsing
  complexity and edge cases.) Governs R2, R9.
- **Usage is matched by the action fired, not the literal key combo.** Keeps
  completion tracking correct even for a rebound key; the trade-off is a
  display/reality mismatch in the shown shortcut text, which is accepted as
  a known limitation of the static-pool decision above. Governs R7.
- **Pool exhaustion ends in an all-learned state rather than looping or
  hard-stopping at a small fixed list.** Shipping a pool larger than the
  visible list keeps the rotation meaningful for longer without turning it
  into an endless grind. (session-settled: user-approved — chosen over
  recycling completed bindings back into rotation, or stopping at a small
  fixed list.) Governs R9, R11.
- **Rotation order is fixed and curated, not random.** Lets the author
  sequence learning deliberately (e.g., most essential bindings first).
  (session-settled: user-approved — chosen over random selection from the
  remaining pool.) Governs R9.
- **No manual "mark as known" control.** Keeps completion honest — it only
  ever reflects real usage — and avoids extra UI and state for this scope.
  (session-settled: user-approved — chosen over adding a skip/complete
  button for already-known bindings.) Governs R10.

## Key Flows

- **F1 — Open and view the list (v1 and v2).** User clicks the top-right
  menu entry → the box opens showing the current list, in curated order (v1)
  or current rotation state (v2) → user reviews it → closes the box.
- **F2 — Background counting (v2).** User triggers a tracked keybinding at
  any time, box open or closed → the counter for that keybinding's
  underlying action increments in the background. Covers R5, R7.
- **F3 — Completion and rotation (v2).** A keybinding's counter reaches 10
  → it's marked complete and moved to the bottom of the visible list → the
  next not-yet-learned keybinding from the curated pool is inserted at the
  top → background counting continues for every keybinding in the pool,
  completed or not. Covers R8, R9, R5.

## Acceptance Examples

- AE1. Given a keybinding's counter is at 9, when the user triggers it once
  more, then it reaches 10, is marked complete, moves to the bottom of the
  list, and the next uncompleted keybinding from the pool appears at the
  top. Covers R8.
- AE2. Given the box is closed, when the user triggers any tracked
  keybinding, then its background counter increments even though no UI is
  visible. Covers R5.
- AE3. Given the user has personally rebound a keybinding's default key
  combo to a different key, when they trigger it via their custom key, then
  usage still counts toward that keybinding's completion, and the displayed
  key text remains the shipped default. Covers R7.
- AE4. Given every keybinding in the curated pool has reached completion,
  when the last one completes, then the plugin shows an all-learned state
  instead of pulling in a further rotation. Covers R11.

## Scope Boundaries

**Deferred for later:**
- Leaderboard showing other users' stats (keybindings completed, usage per
  keybinding). Would require an opt-in telemetry mechanism and some kind of
  backend/service — neither is addressed by this PRD.
- Letting the user customize which keybindings appear in or get added to
  the curated pool.
- A manual "mark as known"/skip control.

**Outside this plugin's scope entirely:**
- Tracking or displaying usage for application-specific (non-Hyprland)
  keyboard shortcuts.

## Success Criteria

- v1: a user can open the menu entry and see a readable list of ~10 curated
  keybindings with correct key combos and descriptions, styled consistently
  with other built-in Omarchy menu entries.
- v2: a user who uses Omarchy normally sees at least one keybinding reach
  completion and rotate during ordinary day-to-day use, with no action
  required beyond their normal keyboard use.

## Assumptions

- Single local user, single machine — no accounts, sync, or multi-user
  concept in v1/v2.
- Upgrading from v1 to v2 starts every counter at zero; v1 tracks nothing,
  so there's no usage history to carry forward.
- "Top-right menu" refers to whatever menu surface Omarchy already exposes
  for built-in quick-access items; this plugin adds one entry there rather
  than introducing a new menu system.

## Outstanding Questions

**Deferred to Planning:**
- Does a row's counter update live while the box is open, or only reflect
  the count as of when the box was last opened?
- Once a keybinding is complete, does its displayed counter keep showing
  the running total past 10, or switch to a fixed "Complete" indicator?
- Exact content of the curated ~10 (and the larger pool) — which
  keybindings, their descriptions, and their priority order. This is content
  curation, not a structural decision, and can be authored during
  implementation.
